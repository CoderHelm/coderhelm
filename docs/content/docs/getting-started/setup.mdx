---
title: Set up repos
description: How CoderHelm reads each repository, recommends a value for every setting with the reason next to it, and applies them for you or after you review each one, with undo for one setting or a whole run.
---

**Setup** is the first item in the dashboard's left menu. You pick repositories, CoderHelm reads each one and recommends a value for every setting it manages, and then either turns them on for you or shows you each one first. Every run is saved to the audit log and can be undone.

Running Setup is an admin capability by default, and a [custom role](/concepts/roles) can include it. Each change also needs the permission its own settings page needs. Anyone who may change any setting sees Setup in the menu and the state of each repository. A setting that needs a permission you don't have is marked "needs" with that permission's name, and stays as it is.

## Two ways to run it

| | Do it for me | Review each setting |
| --- | --- | --- |
| **What you do** | Pick the repositories and click once | Pick the repositories, then choose Use, Keep or Edit for each recommendation |
| **Your own settings** | A value someone chose for a repository stays (you can switch this off); one the repository argues against is listed first as worth a look | You see each one next to the recommendation |
| **Settings that close or merge** | Start as a preview that changes nothing until you switch it on | You see what each would have done; auto-merge turns on only when you pick Use for it |
| **When it finishes** | A results page with what changed, what was kept and what waits as a preview | A results page with what changed on each repository |

**Do it for me** is the recommended choice. Use **Review each setting** when you want to see every value before anything changes.

Both start the same way, from the Setup page, from a repository's row, or from **Set up repos** in the command menu (Command K on a Mac, Ctrl K elsewhere). The first step picks **Which repos**: the ones not set up yet, all of them, or the ones you pick, with **Only what's new** to look at new recommendations only. The button says what happens: **Set up 3 repos for me** or **Analyze 3 repos**. Do it for me then reads and applies in one step and shows the results; Review each setting reads, shows the Review step, then applies.

## What CoderHelm reads

Each recommendation is labelled with where it came from:

| Label | Meaning | Examples |
| --- | --- | --- |
| **Detected** | Read straight from the repository or GitHub | The test runner in `package.json`, the workflows that run your end-to-end tests, the labels a workflow reacts to, branch protection and its required checks, the pull request template, `CODEOWNERS`, `AGENTS.md` and `CLAUDE.md` |
| **Inferred** | A judgment from those facts and the repository's last 50 merged pull requests | The review focus, whether to require tests, coder instructions, which CI labels to add, how long before a pull request counts as stale |
| **Default** | Nothing in the repository says otherwise, so CoderHelm's own default | |

Each recommendation shows its evidence beside it, with a link to the file when there is one. Inferred values are suggestions: check them before you rely on them.

Reading uses tokens from your team's monthly budget. The estimate shows as soon as you pick the repositories, before anything starts, and a run that doesn't fit what is left of your monthly limits can't start. While it reads, the estimate shows next to what it has used so far. Reading itself changes nothing.

## Your settings are not overwritten by surprise

Only a value someone chose for that repository counts as yours: one saved for the repository itself, the repository named in a team list (such as the security policy's or the Tests page's repositories), or a team-wide value someone changed from its default. A repository missing from a team list, a default, and a value an earlier Setup run wrote on its own are not choices.

- In **Do it for me**, **Keep what someone chose** is on by default: everything else takes the recommendation. A choice the repository's own files argue against (for example, test results off while a workflow runs tests) is kept and listed first as **Worth a look**, with the file. Switching it off reads **Replace mine with recommended**, and the page warns you before you start.
- In **Review each setting**, the choice at the top of the Review step is **Keep my settings**, **Use recommended everywhere** or **Decide one by one**. When applying would replace a value someone chose, the page lists each one and asks before it applies.

A setting someone changes by hand after Setup applied it is marked **Custom**. Later runs leave it alone unless you choose to replace it.

## Settings that act on their own

Some settings close, merge or post things: closing stale pull requests, merging when checks pass, and opening security fix pull requests. Their recommendation shows what they would have done over the last 14 days, for example how many pull requests would have been marked stale and closed.

Anything that closes or merges starts as a preview, in both ways of running Setup:

- Stale pull request closing is turned on with its dry run on: it reports what it would mark and close, and changes nothing.
- Auto-merge is only recommended where branch protection requires checks, with how many pull requests it would have merged in the last 14 days. No choice at the top turns it on, not even **Use recommended everywhere**: it stays off until you pick **Use** for it in Review, or switch it on from the results.
- Security fix pull requests follow your security policy's schedule, and the evidence names it.

**Switch on** on the results page turns a preview into the real setting in one click. It is recorded like any other change, so **Undo** puts it back as a preview.

## Results, retry and undo

The results page shows each repository:

- a one-line summary, such as "Turned on 9, 2 worth a look, 2 previews to switch on, kept 3 settings someone chose", whose numbers are the lists under it;
- lists of what is worth a look, what was turned on, what was kept and what waits as a preview, each with its evidence. Each kept setting says who set it, where and when (or that it was set before Setup tracked who), and has **Use recommended**; **Use recommended for all** takes a whole list. Each is recorded like any other change, with its own **Undo**.

Team-wide settings (one value for every repository, such as the alert budget, git conventions and the security policy's fix pull requests) are listed once, in their own section, never inside one repository's result.

Setup changes CoderHelm's own settings only. It opens no pull requests in your repositories; the test setup pull request is still opened from the **Tests** page.

If a repository fails, its reason shows on its row, and **Retry the failed repo** (or **Retry the 2 failed**) runs again for the failed repositories only. On the Setup page, a failed repository's row has **Try again**.

On the results of **Do it for me**, **Undo** next to a change puts that one setting back. **Undo this run**, on the results of either way, puts back every setting the run changed, after you confirm. A setting someone changed again after the run is left as it is and listed. Every change, and every undo, is recorded in the audit log.

## New recommendations and new repositories

When a CoderHelm release adds a recommendation, Setup lists it under **New recommendations** and counts it on the menu badge. Nothing new turns itself on. Review it on every repository, or dismiss it; a dismissal is for the whole team.

The badge counts new recommendations plus repositories not set up yet.

A newly connected repository starts as **Not set up**. The team setting **Set up new repos on their own** (off by default) applies the choices from your last reviewed run to new repositories and lists what it changed on the Setup page.

## What each repository has on

Open a repository's row on the Setup page to see every feature: on, a preview, off or not used here (nothing in the repository for it to work on, such as release notes with no release tags; these don't count against the total), each with its settings in words, whether they match the recommendation, why, and a link to its settings page. The row itself reads, for example, "5 on · 2 previews · 4 off", with the reasons in one line under it.

## Repository states

| State | Meaning |
| --- | --- |
| **Not set up** | Setup has never run on this repository |
| **Set up** | Every setting matches what Setup last applied |
| **Custom** | Someone changed a setting by hand after Setup applied it |
| **Update available** | A CoderHelm release added recommendations this repository hasn't reviewed |
| **Failed** | The last run couldn't change some settings here; the reason is on its row |
| **Analyzing** | CoderHelm is reading the repository now |

## On the settings pages

On the reviewer, stale pull request, tests, security, workflow, instructions and alerts settings pages, a setting whose value is what Setup recommends is marked **Recommended**, and one changed by hand after Setup applied it is marked **Custom**. **Review in Setup** at the top of those pages (all of them except stale pull requests) opens Setup: for the repository you picked on the page, or for every repository on a team-wide page.
