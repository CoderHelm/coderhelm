---
title: The PR reviewer
description: Turn on CoderHelm's reviewer for your team's pull requests, and control what it checks, when it merges and what it learns.
---

The reviewer reviews pull requests written by people (and by CoderHelm). It posts a real GitHub review, either **Approve** or **Request changes**, with comments on the lines that matter, and a risk level of low, medium or high. Changes that touch migrations, authentication, secrets or payments are always rated high.

## What a review looks like

The review opens with a **PR Overview**: one sentence on what the pull request does, a short **Changes** list, and a **Reviewed Changes** table with one line per changed file. When more than 15 files changed, the table is folded so the review stays short. The verdict and the findings follow, and each finding is also a comment on the line it is about.

## When it requests changes

It requests changes only for a named correctness, security or data-loss problem, with the file and line and the evidence that shows it (the code path, a test or CI result, a data query, or the documentation of the tool involved). Before it posts, a final check looks at the whole pull request and its threads; when nothing named holds up, it approves instead and says what it assumed.

Every other finding is a labeled note on the approval:

| Label | What it is |
| --- | --- |
| **Nit** | A style, naming or layout preference |
| **Suggestion** | An optional improvement, hardening, a refactor, a missing test, or a written team rule the change doesn't follow with no defect shown |
| **FYI** | A question, a fact worth confirming, or a concern nothing in the change could show |

A request for changes lasts only while what it names does: once those threads are fixed or answered, the next review approves.

## Turn it on

1. Open **Reviewer**, then **Reviewer settings**, and pick a repository.
2. Switch on **Enable reviewer for this repo**.
3. Keep the **Trigger label** `ch-review`, or change it.

Add the label to a pull request to get a review. Once a pull request has the label, every new push is reviewed again. Draft pull requests are skipped until they are marked ready.

## Follow a review while it runs

While a review runs, the pull request shows a **CoderHelm review** check. Its **Details** link opens the review's session in CoderHelm: the steps so far, live while it runs, and the verdict with a link to the posted review once it is done. Each review has its own session, so an older check keeps showing its own review.

The session shows every step the reviewer took, grouped the way it worked: the searches it ran (with each query), the files it read (with the lines), the folders it listed and the other lookups it made, the short notes it wrote on what it was checking, and the comments it kept. Open a group to see its entries; the time beside each one is how far into the review it happened. Only where the reviewer looked is kept, never the contents it read, and secrets are removed before anything is saved. A long review keeps its first 200 steps and says how many more there were. The same page shows the review's PR Overview with its file table.

When the review is done, the check ends as neutral if the review has findings, and as success when it found nothing. The check needs the **Checks** permission on the GitHub App. Without it, reviews work as before, just with no check on the pull request.

## What it reads from GitHub

- **CI on the pull request.** Both check runs and commit statuses, so CI that reports through statuses (an external CI server, a preview deploy bot) counts: a red status is a failing check, and a pending one is CI still running. Without **Commit statuses: read**, CoderHelm reads check runs only and says so where it decides, for example "CI was read from check runs only because CoderHelm can't read Commit statuses on this installation; add Commit statuses: read to the GitHub App."
- **GitHub Code Quality findings.** When a repository runs GitHub Code Quality, the open findings on the files a pull request changes are given to the reviewer, so it never reports one a second time, and it says "fixes N code quality findings" when the change fixes some. This needs **Code quality: read**; without it, or with Code Quality off, reviews work as before.
- **Deploys.** Analytics counts where CoderHelm's runs deployed from GitHub's deployments when a repository records them, and reads the workflow otherwise. Without **Deployments: read**, the Analytics page says deploys were inferred from workflow names and jobs.
- **CI logs.** When its own pull request fails CI, CoderHelm reads the failing jobs' logs from the newest attempt, with the step each failed in, and is told which jobs failed once and passed when re-run, so it doesn't chase a flaky one. Without **Actions: read**, it reads check annotations instead and says so.

## Talk to it on a pull request

| Comment | What happens |
| --- | --- |
| `@coderhelm re-review` | Reviews the latest commit again. GitHub's **Re-request review** button does the same. |
| `@coderhelm <question>` | Answers a question about the change, in the thread. |
| `@coderhelm stop auto-merge` | Stops an automatic merge. The stop holds until someone resumes it. |
| `@coderhelm resume auto-merge` | Re-arms auto-merge; every check is evaluated again from the start. |
| `@coderhelm keep open` | Keeps the pull request open: it is never marked stale or closed as stale. From its author or anyone with write access. See [Stale pull requests](/getting-started/stale-pull-requests). |

## Settings

| Section | What you can set |
| --- | --- |
| Reviews | On or off, trigger label, what to focus on |
| Tests | Check the change by running tests (a failing run requests changes); require tests (a missing test is a Suggestion, and CoderHelm writes tests for its own changes) |
| CI labels | Labels it may add, labels that must go together, guidance |
| Auto-merge | Merge when it approves, merge method, deploy labels, also require a person's approval |
| Tags and health check | Tag after merge, tag style and prefix, batch window, health check after merge |
| Release notes | Where notes are written: GitHub, a Confluence page, a webhook; a writing guide |
| Review reminders | Remind people in Slack or Teams |
| Stale pull requests | Opened from the **Stale pull requests** button at the top of the page. See [Stale pull requests](/getting-started/stale-pull-requests) |

## Auto-merge is careful

When auto-merge is on, CoderHelm merges only the exact commit it reviewed and approved, and only after CI passes. A new push means a new review. If anyone stops it, it stays stopped until a person re-arms it.

## It learns from pushback

When someone disagrees with a review (replies under a comment, dismisses the review, merges anyway, or closes the pull request unmerged), CoderHelm waits ten quiet minutes and then decides whether the review was wrong. If it was, it writes one general lesson for that repository or the whole team, and uses it in later reviews. Admins can read and delete lessons on the **Reviewer** page. People can also rate any review with a thumbs up or down.

## Stale pull requests

Off by default. Turned on, CoderHelm marks a pull request stale after 21 days with no activity from a person, warns on it, and closes it 7 days later if nothing happened, with a comment that says how to reopen. Its own comments and other bots never count as activity, exempt labels and drafts are never touched, it starts as a dry run, and the branch is kept. Open it from the **Stale pull requests** button at the top of **Reviewer settings**.

How it decides, every setting, the dry run and how to keep one open: [Stale pull requests](/getting-started/stale-pull-requests).

## Release notes

With release notes on, every release tag gets notes written from the merged pull requests, published to GitHub and, if you set them up, Confluence and email. They are listed on the **Releases** page.
