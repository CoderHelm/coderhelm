[Security fixes](/getting-started/security-fixes/) checks the packages your code imports. Infrastructure vulnerabilities checks what you actually run on AWS: the AMIs and kernels of your instances, your EKS clusters and node groups, the container images your services run, your databases, caches and OpenSearch domains, ECS services on Fargate, and the Lambda runtimes in your code. For each one it says whether you have to act, opens the fix pull request or shows the exact step in AWS, and marks what AWS patches for you.

It is off for every AWS account until an admin switches it on, in **Settings**, then **Integrations**, then **AWS**, on the account. Findings show in **Security**, then **Infrastructure**, and what runs in each account shows in **Insights**, then **Infrastructure**, under **Running in AWS**, beside the code review of your infrastructure code. Each resource there lists its versions, where it is defined, what AWS has pending for it and links to its open findings. **Insights**, then **Analytics**, shows the last 30 days: open and fixed findings, the median time to fix, and fix pull requests against steps in AWS.

## The Infrastructure page

Four tiles count what **Needs action now**, the **Fix pull requests**, the **Steps in AWS** and what is **AWS-managed**. Filter the rows by tier or by fix (pull request or in AWS). Each row opens to the fix, where the resource is defined, how to roll it out or what to run in AWS, AWS's date, the advisories and the resources it covers. Admins can open a fix pull request at once with **Open fix PR**, even when security fixes are in a dry run, and read every account again with **Check accounts now**. An account whose role lacks the reads shows **Update the role in AWS**.

## Where the vulnerabilities come from

These public sources are read once a day for every team. Nothing about your accounts is sent to read them.

| Source | What it gives |
| --- | --- |
| **AWS security bulletins** | The feed lists the last 30 days of bulletins. CoderHelm reads each bulletin's page for its per-service section: who has to act for each service (you, you in AWS, AWS, or nobody because it is not affected), the fixed AMI releases, the named service updates, and when patched Fargate tasks started. |
| **Amazon Linux advisories (ALAS)** | Every Amazon Linux 2023 and Amazon Linux 2 advisory. For kernel and important advisories, the page with the first fixed Amazon Linux 2023 release and the new package versions. |
| **Bottlerocket advisories** | Every advisory with its fixed kernel and package versions. |
| **Lambda runtimes** | AWS's deprecation dates for each runtime. A deprecated runtime gets no more patches. |
| **AWS's latest AMI parameters** | The current ECS, EKS and Bottlerocket images, which a fix points to. |

A source that can't be read, or whose page changed its format, keeps its last good copy. The **Sources** list at the bottom of **Security**, then **Infrastructure**, shows each source (Amazon Linux 2023 and Amazon Linux 2 separately) and your AWS accounts, with when each was last read, and "Last read failed" with the reason when the latest read failed.

## What it reads in your account

With the option on, CoderHelm reads each account once a day through the same read-only `CoderHelmLogReader` role, in the account's region. These are describe and list calls only:

| Permission | What it is for |
| --- | --- |
| `ec2:DescribeInstances`, `ec2:DescribeImages` | Which AMI each instance runs, and the release in the AMI's name. Whether it has a public IP address. |
| `autoscaling:DescribeAutoScalingGroups` | Which instances one fix changes together, and their launch template. |
| `elasticloadbalancing:DescribeTargetGroups`, `elasticloadbalancing:DescribeLoadBalancers` | Whether an Auto Scaling group or a service sits behind an internet-facing load balancer. |
| `eks:ListClusters`, `eks:DescribeCluster`, `eks:ListNodegroups`, `eks:DescribeNodegroup` | Each node group's release version and AMI type, and whether the cluster uses Auto Mode. |
| `rds:DescribeDBClusters`, `rds:DescribeDBInstances`, `rds:DescribePendingMaintenanceActions` | Engine versions, whether a database is publicly accessible, and the OS updates AWS has waiting for it. |
| `elasticache:DescribeServiceUpdates`, `elasticache:DescribeUpdateActions` | The self-service updates waiting for each cache, and AWS's apply-by date. |
| `es:ListDomainNames`, `es:DescribeDomains` | OpenSearch service software updates. |
| `ecr:DescribeImageScanFindings` | ECR's own scan results for the images your services run. |
| `ssm:ListInventoryEntries` | The installed kernel, for instances managed by Systems Manager. |
| `ssm:GetParameters`, on `arn:aws:ssm:*::parameter/aws/service/*` only | AWS's public latest AMI in your region. |

ECS services on Fargate are read with the ECS permissions the role already has.

What it never reads:

- **Lambda function settings.** `lambda:ListFunctions` and `lambda:GetFunctionConfiguration` both return environment variables. CoderHelm finds your Lambda functions and their runtimes in your Terraform instead.
- **User data.** It never reads launch template versions or instance attributes.
- **Anything it would change.** CoderHelm opens pull requests in your code and shows the AWS steps for a person to run. It never runs them.

Switching the option on when the role lacks these reads shows a warning that names the feature, with the one-click update: an AWS admin signs in to the account and creates the update stack, which adds only these permissions. The stack's `InfrastructureVulnerabilities` parameter is set to `on` by the link.

On a self-hosted install, accounts you connect with their own role work the same way. The install's own account is different: there is no stack for you to launch, so you turn these reads on from the AWS card instead.

## Turning reads on from the AWS card

**Settings**, **Integrations**, **AWS** shows each account's role. What the role still needs is split in two:

- **Needed now**: a read-only permission this release uses that the role doesn't have yet.
- **Optional, off**, collapsed: infrastructure vulnerabilities, Amazon Inspector findings and AWS Health events. They are never needed, so they never make the card say an update is needed.

For an account you connected with its own role, **Turn on in AWS** opens the role's one-click update stack with that read's parameter set to `on`. An AWS admin creates the stack, and the card checks again by itself when you come back.

For a self-hosted install's own account, the card does it for you. Install admins see:

- **Update now to add it** when a permission arrives with a newer release. It is the same update as **Settings**, **System**, with the same review of anything it would change.
- **Arrives with the update installing now** while that update runs.
- When the running version already grants the permission, the reason it is still missing (the install's permission limit, or a change made to the role in AWS) and the fix.
- A **Turn on** or **Turn off** switch for each optional read. CoderHelm prepares a change to the install's own stack that sets only the `InfrastructureVulnerabilities`, `InspectorFindings` or `HealthEvents` parameter, on the version you run. The card lists the read-only permissions it adds, and nothing changes until you press **Confirm and turn on**. It runs through the install's update role like a version update, appears in the update history with who confirmed it, and AWS puts everything back if it fails.

Infrastructure vulnerabilities are on by default on the install's own account; Inspector and Health are off. The reads also need the install's permission limit to allow them. When it doesn't yet, the card says so: an AWS admin applies the install's access update once (**Settings**, **System**, **Permissions**), because no update can widen that limit.

## Three kinds of fix

Matching is by version, with no model, so it costs no tokens. One row is one fix: one AMI, one node group, one database. However many advisories that fix clears, it is still one row.

| Fix | When | What you get |
| --- | --- | --- |
| **Fix PR** | The change is in the code that defines the resource. | A pull request that points the AMI at AWS's latest parameter, sets a node group's `release_version`, changes a Lambda `runtime` or bumps a Dockerfile `FROM`. It goes through the same daily run and token limits as dependency fixes. When rolling the change out needs a step, such as an instance refresh, the exact command is shown with it. |
| **Runbook** | The change happens in AWS, not in code. | A card with the exact AWS CLI command, the path in the AWS console, and AWS's apply-by date: apply an RDS OS update, an ElastiCache service update or an OpenSearch software update. CoderHelm never runs it. |
| **AWS-managed** | AWS patches it itself. | A row with the bulletin's reason, collapsed at the bottom. It is never counted as open and has no tier. |

Where the code is comes from the resource's tags (a `Repo` tag, its CloudFormation stack), or from a search of your connected repositories for its AMI, group or name. For Terraform that is the file and the resource address, such as `aws_launch_template.web`.

Urgency uses the same tiers as dependency fixes. Whether the internet can reach the resource takes the place of whether your code reaches the vulnerable part: a public IP address, an internet-facing load balancer or a publicly accessible database.

A finding closes only when CoderHelm reads the account again and sees the fix running, such as the new AMI on every instance. A merged pull request isn't enough. That also catches a fix that was merged but never rolled out.

## A worked example: bulletin 2026-160-AWS

CVE-2026-98432 is a use-after-free in the Linux kernel's IPv4 TCP code, rated Important. The bulletin's per-service section says who acts. Take a team that runs:

- an Auto Scaling group of three Amazon Linux 2023 instances on release `2023.12.20261020`, behind an internet-facing load balancer;
- an EKS managed node group on release `1.31.0-20261015`;
- an ECS service on Fargate;
- a zip Lambda function on `python3.12`;
- an Aurora PostgreSQL cluster.

**Security**, then **Infrastructure**, shows exactly this:

| Row | Fix | Why |
| --- | --- | --- |
| Auto Scaling group `web-asg` | Fix PR, P1 | Amazon Linux 2023 is fixed in release `2023.12.20261102`. The pull request changes `aws_launch_template.web`, then an instance refresh rolls it out. Internet-facing, so P1. |
| EKS node group `prod-ng` | Fix PR, P2 | EKS optimized AMIs are fixed in `v20261031`. The pull request sets the node group's `release_version`. |
| Aurora cluster `orders` | Runbook | The bulletin says to apply the database OS update, and RDS lists it as pending with a date. The card shows `aws rds apply-pending-maintenance-action` with the cluster's ARN. |
| ECS service `api` on Fargate | AWS-managed | Tasks started after the fix run patched, and AWS retires older ones. Forcing a new deployment replaces them sooner. |
| Lambda `thumbs` | AWS-managed | The bulletin says Lambda is not affected. |

The EKS control plane, load balancers and CloudFront are AWS's as well. They aren't listed, because nothing of yours runs there.

## Inspector and AWS Health

Both are optional, switched on in **Security**, then **Policy**, under **Infrastructure**, and both depend on something on your AWS account:

- **Amazon Inspector** is billed by AWS: about $1.25 per instance a month, $0.09 per container image scan, and $0.30 per Lambda function a month. When you turn it on and CoderHelm may read its findings, they take the place of CoderHelm's own matching for the resources Inspector covers. They also add whether an exploit is known and whether the network can reach the vulnerable port.
- **AWS Health** names your own affected resources for some bulletins. Its API needs AWS Business Support or higher. Without that plan, choose **EventBridge rule in your account**: a CloudFormation template you download adds a rule that forwards the same Health events. With Inspector findings, a row can also say **Exploit known** or **Reachable (Inspector)**.
