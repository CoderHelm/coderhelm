---
title: Security fixes
description: How CoderHelm checks each advisory that touches your dependencies against your code, opens as few fix pull requests as it can (one per repository by default), and posts the urgent ones to your alerts channel with a deadline.
---

When an advisory is published for a package one of your repositories uses, CoderHelm works out whether your code actually reaches the vulnerable part. It then gives the finding a tier and a deadline, opens a fix pull request and gets its CI green. For urgent findings it also posts a card to the same channel as your production alerts.

Security fixes are off for new teams. Turn them on in **Security**, then **Policy** (admins only), and pick what it does:

- **Open fix PRs (recommended).** CoderHelm opens fix pull requests and posts cards per the policy, within the [daily limits](#daily-limits).
- **Preview first.** CoderHelm finds, checks and ranks findings but opens nothing and posts nothing. **Preview** shows what it would do, and you can still [open a fix PR by hand](#opening-a-fix-pr-by-hand).

## Where the advisories come from

| Source | What it is used for |
| --- | --- |
| **OSV.dev** | The main advisory database, covering the common package ecosystems. CoderHelm asks OSV's API about the packages and versions in your stored dependency lists. |
| **Dependabot alerts** | The fastest signal when Dependabot alerts are on for a repository. CoderHelm hears about each alert as it is created, fixed, dismissed or withdrawn, and reads its direct or indirect and runtime or development details. |
| **GitHub advisories** | Every new GitHub advisory is checked against the stored dependency list of each repository, including repositories where Dependabot alerts are off. |
| **Your repository's own advisories** | Advisories a repository publishes about its own code, and private vulnerability reports sent to it. Each is a finding in the repository's code, and triage looks for the functions it names. A report still in triage or draft is private: the team sees it in CoderHelm, but it is never posted to a channel and never fixed in a public pull request or issue. This needs **Repository security advisories: read** on the GitHub App; without it the other sources work as before. |
| **CISA's known exploited list** | Vulnerabilities being exploited now. Its due date for each one can become the deadline. |
| **FIRST EPSS** | A daily score for how likely each vulnerability is to be exploited in the next 30 days. |

OSV and GitHub data are licensed CC-BY, so the dashboard and every pull request credit them.

CoderHelm stores each repository's dependency list when its default branch changes, so a new advisory is a lookup, not a scan of every repository.

The **Sources** panel on the Security page shows each source with what it gives, its state, when it was last read and how many findings came from it, and the dependency list of each repository: its package count, its ecosystems, when it was read, or why it couldn't be. The list comes from GitHub's dependency graph, so a repository with the graph off says so: turn it on in the repository's **Settings**, then **Code security**.

### What is sent where on a self-hosted install

Your dependency lists are stored in your own AWS account. To check them, the install makes these outbound calls. The OSV call is the only one that carries anything from your repositories, and it is package names and versions, never code:

- OSV's API (`api.osv.dev`), with the package names and versions from your dependency lists, never your code;
- CISA's exploited list (a public JSON file), a few times a day;
- FIRST's EPSS scores, for the vulnerability IDs the install holds;
- GitHub's API, as for everything else CoderHelm does.

## The four verdicts

Each finding goes through cheap checks first: the version ranges, then whether the package is loaded at runtime (a development-only package is not loaded). For the rest, CoderHelm searches the code for where the package and the functions the advisory names are used. When no file names them, the verdict is unknown with that reason, and no model is asked. Otherwise the agent reads those places once per package version, for every advisory it has together, and writes a verdict with file and line evidence. The verdict is reused until the code that uses the package or the advisories change.

| Verdict | Meaning |
| --- | --- |
| **Reachable** | Your code calls the vulnerable part of the package. |
| **Present, not reachable** | The package is loaded, but nothing calls the vulnerable part. |
| **Not loaded** | Development or test only, never loaded in production. |
| **Unknown** | The evidence is missing, with the reason (for example, "tar is imported in 3 files, but the advisory names no functions to look for"). |
| **Checking** | Not read yet. Its tier is provisional until it is. |

Each verdict comes with its evidence: the files and lines that show it, the dependency path, what was checked and how confident CoderHelm is. A verdict never closes an alert on its own. "Not reachable" lowers the tier and shows its evidence; only a person can dismiss a finding.

## Tiers and deadlines

These are the defaults. You can change when each tier gets a pull request, which tiers post to the alerts channel, and the number of days for each deadline. With one pull request per repository (the default, see [Pull requests](#pull-requests)), the tiers' timing decides when the repository's pull request starts.

| Tier | When | What CoderHelm does | Due |
| --- | --- | --- | --- |
| **P0** | Evidence only: on the exploited list and loaded at runtime; or CVSS 9 or more and reachable; or a malicious package | Opens the pull request at once and posts a card | 3 days, or the exploited list's date when sooner |
| **P1** | CVSS 7 or more and reachable; an EPSS score of 0.1 or more; or a high score, a runtime dependency and an unknown verdict | Opens the pull request within the hour and posts a card | 7 days |
| **P2** | Reachable and medium; or high but not reachable | Opens pull requests once a day, grouped by ecosystem | 30 days |
| **P3** | Development only, not loaded, or low | One grouped pull request a week, with no notifications | 90 days |

The defaults follow CISA BOD 19-02 (critical in 15 days, high in 30), PCI DSS 4.0.1 requirement 6.3.3 (critical within a month) and FedRAMP's deadlines by exploitability and exposure.

An unknown or still-checking verdict is never P0 on its score alone, and a missing score is never read as a high one.

## Daily limits

Security never runs away with your tokens. These limits are in the policy, with these defaults:

| Limit | Default | What happens past it |
| --- | --- | --- |
| Fix runs a day | 3 (0 to 20) | The rest wait, the most urgent first, with "Waiting: today's 3 fix runs are used. Next starts tomorrow." Adopting a Dependabot or Renovate pull request, or opening an issue, doesn't count. Only one fix run per repository at a time. |
| Fix run tokens a day | 2 million | No new fix run starts until tomorrow. |
| Reachability check tokens a day | 400,000 | The rest say "waiting for tomorrow's check". |
| Cards a day | 10 | One digest card says how many more are waiting. |

The Security page shows the day's spend ("Checked 38 packages today, 92k of 400k tokens") and the month's. **Analytics**, then **Security**, shows findings opened and fixed, fix pull requests, the time to fix by tier and the tokens per day, and the usage breakdown lists security checks and security fix runs on their own lines.

## Pull requests

The policy's **Pull requests** choice decides how many there are:

| Choice | What you get |
| --- | --- |
| **One PR per repo (fewest PRs, recommended)** | Every due fix in a repository, across all its ecosystems, in one pull request. The default for teams that turn Security on. |
| **One per ecosystem** | The same, one pull request per repository and ecosystem (npm, Python, Go...). |
| **One per package** | P0 and P1 get a pull request per package; P2 and P3 are grouped per repository and ecosystem, daily or weekly. A policy saved before this choice existed keeps this. |

With one per repository, the most urgent fix sets when the pull request starts: a P0 starts it at once and brings everything else that is due or waiting in that repository; otherwise it starts once a day. A repository with 57 package fixes gets one pull request, not 57.

A repository has one open security pull request at a time. New fixes join it: a follow-up run on the same pull request pushes their bumps to its branch, and the title, description and labels are written again to count them. Nothing opens a second one while the first is open.

Major version bumps stay in the pull request. When CI fails, CoderHelm fixes it in the same pull request. Only when it can't get CI green with a major bump in it does that bump leave: a follow-up run reverts it on the branch, and it gets a pull request of its own. With **Open an issue only** for major bumps, they never join the pull request.

A pull request counts as one fix run against the [daily limits](#daily-limits), however many packages it bumps, and its tokens, follow-up runs included, count against the token limit.

## Opening a fix PR by hand

Admins can pick findings on the Security page and send them as one pull request:

1. Pick rows, or use the quick selects above the list: **Select everything fixable**, **Select P0 and P1**, or a repository. `x` picks the row under the pointer, shift-click picks a range, and `Esc` clears.
2. The bar at the bottom says what the selection becomes, for example "14 fixes selected in web-app: 1 pull request · 31 advisories · 2 major upgrades". **Fix in one PR** makes one pull request per repository, whatever the policy says; a pull request lives in one repository, so a selection across two repositories is two. The menu beside it offers **One PR per package**.
3. A review opens in the page before anything runs. It shows each pull request's title, branch and labels, and every package bump with its versions, advisories and verdict; any row can be taken out. It warns about major upgrades, says what is left out and why (no fixed version yet, already in a pull request), and says when the fixes are added to the repository's open security pull request instead of a new one. It shows the cost against today's limits: "Uses 1 of today's 3 fix runs · estimated 180k of 2M tokens".
4. Confirming starts the runs and links each one.

From a finding's page, **Open fix PR** opens a pull request for that package, and **Add to the open PR** adds the fix to the repository's open security pull request (or starts one).

A request starts at once even in a preview, for those findings only, within the daily limits; past them the rest wait for tomorrow, unless the admin raises today's limit for that request, which is recorded in the audit log.

## The pull request

One pull request per repository by default, never one per alert. The same flaw listed under its CVE, GHSA and ecosystem IDs counts once, and a bump that clears three advisories is one bump.

- **Branch:** `coderhelm/security-updates-<date>-<id>`, or `coderhelm/security-<package>-<version>` for one package.
- **Title:** `fix(deps): security updates for <repo> (14 packages, 31 advisories)`; for one package, `fix(deps): bump <package> <from> to <to> [SECURITY] (<ID>)`. The prefix follows your repository's commit style, or your team's git conventions.
- **Labels**, created when missing:
  - the labels you set in the policy (by default `security` and `dependencies`);
  - `severity:critical`, `severity:high`, `severity:medium` or `severity:low`, the highest of its fixes;
  - `reachable`, `not-reachable` or `reachability:unknown`;
  - `exploited` when it is on CISA's list;
  - `breaking` when a major version bump was needed;
  - the ecosystem label Dependabot would use, so your existing filters keep working.
- **Body:** a summary with the tier and due date; for a pull request with several packages, a table of every bump with its advisories, reachability and due date; the advisory (IDs, CVSS, EPSS, the exploited list, the weakness); what is affected (the dependency path, runtime or development, direct or indirect); the reachability verdict with its files and lines; the change; and the CI run. It ends with the Dependabot alert it closes and the data credit.

The pull request has the public facts about the advisory. How exposed your own production is stays in the dashboard and the card, never in a public repository.

Lockfiles are regenerated with the repository's own package manager, never edited by hand. When a major bump is needed, the policy decides whether CoderHelm fixes the breaking changes in the same pull request or opens an issue only. When Dependabot or Renovate already opened a pull request for the fix, CoderHelm adopts it instead of opening a duplicate.

`security` is already a label the stale pull request cleanup never closes.

## The alert cards

P0 and P1 findings post a card to the same Teams or Slack channels as your production alerts, through your alert routes (**Settings**, then **Alerts**). The card says which repository is affected and why, the fix pull request and its CI, the package versions and the deadline, with buttons to open the pull request and see why.

The same card is updated when the pull request opens, when CI passes and when it merges. It also posts an update at half the deadline and at the deadline, when an open finding is added to the exploited list, and when its EPSS score jumps. A finding your team already handled never posts twice.

## Dismissing and ignoring

**Dismiss** a finding from its page when it doesn't apply (admins only). A reason is required, and you can give a date for it to come back if it still applies. The reason is kept with the finding. When there is a Dependabot alert and the GitHub App has **Dependabot alerts: write**, the alert is dismissed too; with read only, it is recorded in CoderHelm only. **Reopen** undoes it.

**Ignore** an advisory in the policy, for one repository or every repository. Every ignore needs a reason and an end date, so nothing is ignored forever by accident. When the date passes, the advisory is checked again.

## The GitHub App permission to add

Reading Dependabot alerts needs one more permission on the CoderHelm GitHub App: **Dependabot alerts: read**, and the **Dependabot alert** event. Until it has them, the Sources panel says which is missing: the App doesn't ask for it, your organization hasn't accepted it yet, or Dependabot alerts are off for a repository. It is checked again on every sweep, so it clears within about 20 minutes of the fix. CoderHelm still checks your dependencies against OSV and GitHub's advisories, but it hears about new Dependabot alerts later. Dismissing the Dependabot alert from CoderHelm also needs **Dependabot alerts: write**.

- **Hosted:** an owner of your GitHub organization opens GitHub, then **Settings**, then **GitHub Apps**, then **CoderHelm**, and accepts the request for new permissions.
- **Self-hosted:** the App's owner adds **Dependabot alerts: read** under the App's repository permissions and subscribes to the **Dependabot alert** event. Each organization that installed the App then accepts the new permission the same way.
