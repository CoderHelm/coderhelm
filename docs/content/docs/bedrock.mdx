Your team's knowledge bases in CoderHelm hold pages from Notion, Confluence, Google Drive, Sanity, GitHub, websites and uploaded files. There are two ways to use them from Amazon Bedrock. Pick one, or use both.

| | Search live over MCP | Copy into a Bedrock knowledge base |
| --- | --- | --- |
| What Bedrock gets | Two tools, `knowledge_search` and `knowledge_list`, on CoderHelm's MCP server | A Bedrock knowledge base you own, kept in step with CoderHelm |
| Who reads what | Each search reads only the knowledge bases the connection was given, and only while the person who made it can read them in Chat | Everyone with Bedrock access to that knowledge base reads everything copied into it |
| Freshness | Live | Minutes for a custom data source; up to 15 minutes for an S3 folder |
| Setup | A connection made in CoderHelm, pasted into your gateway | Self-hosted: one button that opens a ready-made AWS stack. CoderHelm cloud: a custom data source |
| Works with | Bedrock AgentCore Gateway, Bedrock agents through it, and any MCP client | Bedrock Retrieve and RetrieveAndGenerate, Bedrock Agents, and anything that reads a Bedrock knowledge base |
| Set up in | **Knowledge**, **Use in Bedrock**, **Let Bedrock agents search your knowledge live** | **Knowledge**, **Use in Bedrock**, **Copy into a Bedrock knowledge base** |

Both are for people who manage knowledge bases (admins, or a custom role with **Manage knowledge bases**).

## Search live with AgentCore Gateway

AgentCore Gateway adds a remote MCP server as a target and signs in to it with what you give it ([outbound authorization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html), [MCP server targets](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-MCPservers.html)). For CoderHelm that is a **connection**: a client ID and secret you make in CoderHelm for the knowledge bases you choose.

**Why a connection, and not your own sign-in.** The gateway signs in to CoderHelm as a program, with a client ID and secret it keeps. Signing in as yourself is for apps like Claude and Cursor, which open a browser for you ([Claude, Cursor and VS Code](/mcp)). In detail:

- Gateway can also use a person's sign-in (OAuth authorization code), but only with a client ID and secret registered ahead of time.
- Each person then signs in through the agent's own app.
- CoderHelm registers the apps people sign in with without a secret.

So a connection is the way for Gateway today.

### 1. Create a connection

1. In CoderHelm, open **Knowledge**, then **Use in Bedrock**.
2. Under **Let Bedrock agents search your knowledge live**, choose **New connection**.
3. Tick the knowledge bases it reads (or **Select all**). Each one shows its sources and how many pages it holds.
4. Choose when it stops working. On that date the gateway's searches fail until you make a new connection and paste its secret into the gateway. Shorter is safer if the secret leaks.
5. Choose **Create connection**.

Copy the secret now. CoderHelm keeps only a hash of it, so you see it only this once. The same window has copy buttons for the **client ID** (`chkbc_...`), the **client secret** (`chkb_...`), the **token address** and the **MCP server address**. It also has the gateway setup below with them filled in, as console steps, AWS CLI commands or JSON.

A connection holds one scope, `knowledge:read`. It can search and list knowledge, nothing else: no runs, no reviews, no settings.

### 2. Add it to your gateway

First, save the client ID and secret in AgentCore Identity as an OAuth client. The gateway then asks CoderHelm for an hour-long token whenever it needs one:

```bash
aws bedrock-agentcore-control create-oauth2-credential-provider \
  --name coderhelm-knowledge \
  --credential-provider-vendor CustomOauth2 \
  --oauth2-provider-config-input '{
    "customOauth2ProviderConfig": {
      "oauthDiscovery": { "discoveryUrl": "https://api.coderhelm.com/.well-known/oauth-authorization-server" },
      "clientId": "chkbc_...",
      "clientSecret": "chkb_..."
    }
  }'
```

Then add CoderHelm as a target, with the `credentialProviderArn` the first command printed:

```bash
aws bedrock-agentcore-control create-gateway-target \
  --gateway-identifier <your gateway ID> \
  --name coderhelm-knowledge \
  --target-configuration '{"mcp":{"mcpServer":{"endpoint":"https://api.coderhelm.com/mcp"}}}' \
  --credential-provider-configurations '[{
    "credentialProviderType": "OAUTH",
    "credentialProvider": { "oauthCredentialProvider": {
      "providerArn": "<credentialProviderArn>",
      "grantType": "CLIENT_CREDENTIALS",
      "scopes": ["knowledge:read"]
    } }
  }]'
```

On a self-hosted install, use your own address instead of `https://api.coderhelm.com`.

The secret also works as an API key, for programs that send one: header `Authorization` with the prefix `Bearer ` (`create-api-key-credential-provider`, then `"credentialProviderType": "API_KEY"` with `"credentialLocation": "HEADER"`, `"credentialParameterName": "Authorization"` and `"credentialPrefix": "Bearer "`), or an `X-Api-Key` header without a prefix.

### 3. Test it

In the window that shows the secret, choose **Test the connection**. The page signs in at the token address with the client ID and secret, then calls `knowledge_search` on the MCP server, the same way the gateway does. It shows the passages it found, or what failed in plain words.

The gateway reads the tools when the target is created. Agents then see `coderhelm___knowledge_search` and `coderhelm___knowledge_list` (the gateway puts the target's name and three underscores before each tool's name).

### What the tools return

| Tool | Arguments | Returns |
| --- | --- | --- |
| `knowledge_list` | none | The knowledge bases the connection reads: id, name, description, and whether it is a source of truth |
| `knowledge_search` | `query` (required), `base` (an id or name from `knowledge_list`), `limit` (1 to 20, default 8) | The best passages, each with `text`, `title`, `location`, `link`, `updated_at`, `score`, `base` and `source` |

### Who sees what

- A connection reads as the person who made it, checked on every call: the knowledge bases they gave it, narrowed to the ones they can still read in Chat. If their role changes, the connection follows. If they leave the team, it stops.
- A knowledge base read with each person's own sign-in (such as a search tool that signs each person in) is never read with a connection, because there is no person to sign in as.
- The list of connections shows what each reads, who made it, when it was last used and when it stops working. **Revoke** stops it at once, including access tokens it already got.
- Every call is written to the team's audit log with the connection's name and the knowledge base it searched. The query and the passages are never logged.

People can also give their own MCP apps (Claude, Cursor, VS Code) knowledge search: see [Claude, Cursor and VS Code](/mcp).

## Copy into a Bedrock knowledge base

CoderHelm keeps the knowledge bases you choose copied into a Bedrock knowledge base in your AWS account. Added and changed documents are written again, and deleted ones are removed: a deleted file, a deleted knowledge base, one you take off the list, or turning copying off.

**Read this first.** A Bedrock knowledge base has no per-person access. Everyone with Bedrock access to it, and every agent or application that retrieves from it, can read every document copied into it, whatever their access in CoderHelm or in the app the document came from. So only the knowledge bases you tick are copied, and CoderHelm asks you to confirm this before it copies anything. Knowledge bases connected in place (already searched where they live) are never copied.

Each document is the text of one file or page, with this metadata (you can filter on it in Bedrock): `title`, `link` (the original page, or the knowledge base in CoderHelm for an uploaded file), `source` (`notion`, `confluence`, `upload`, ...), `team`, `base`, `base_id`, `file_id` and `updated_at`.

### CoderHelm cloud: a custom data source

Bedrock's custom data source takes documents pushed straight in, with no sync to run ([direct ingestion](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-direct-ingestion.html)).

1. In the Bedrock console, open your knowledge base and add a data source of type **Custom**. Note the knowledge base's ARN and the data source's ID.
2. Connect the knowledge base's AWS account to CoderHelm if you haven't (**Settings**, **Integrations**, **AWS**). This creates the `CoderHelmLogReader` role, which CoderHelm takes on with your team's private External ID.
3. In CoderHelm, open **Knowledge**, **Use in Bedrock**, **Copy into a Bedrock knowledge base**. Choose **A custom data source**, paste the ARN and the ID, tick the knowledge bases to copy, confirm the warning, and choose **Start copying**.
4. The page shows **Update the role in your AWS account**. Open it: it is a CloudFormation update that adds your knowledge base to the role's `SyncKnowledgeBases` parameter. That adds one policy to the role, which allows only these actions, only on that knowledge base:
   - `bedrock:IngestKnowledgeBaseDocuments` and `bedrock:DeleteKnowledgeBaseDocuments`
   - `bedrock:GetKnowledgeBaseDocuments` and `bedrock:ListKnowledgeBaseDocuments`
   - `bedrock:StartIngestionJob` and `bedrock:GetIngestionJob`
   - `bedrock:GetKnowledgeBase` and `bedrock:GetDataSource`

CoderHelm never uses a Bedrock resource policy that names its own shared role, so no other team can write to your knowledge base.

### Self-hosted: one button

A self-hosted install copies into an S3 folder in its own account, which a Bedrock knowledge base reads ([S3 connector](https://docs.aws.amazon.com/bedrock/latest/userguide/s3-data-source-connector.html)). One button sets it all up:

1. Open **Knowledge**, **Use in Bedrock**, **Copy into a Bedrock knowledge base**.
2. Tick the knowledge bases to copy, and confirm the warning.
3. Choose **Set up in AWS**. The AWS console opens a stack with every parameter filled in. An AWS admin signed in to the install's account ticks the IAM acknowledgement and chooses **Create stack**.
4. The page follows the stack: **Waiting for the stack**, **Creating the bucket**, **Knowledge base ready**, **First sync started**. If the stack fails, the page says why in plain words, for example "The stack failed: VectorBucket: S3 Vectors isn't available in this Region".

The stack makes:
- the bucket that only the install can write;
- a Bedrock knowledge base that stores its vectors in [Amazon S3 Vectors](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors.html) and embeds with Titan Text Embeddings V2;
- the S3 data source;
- a schedule that syncs it every 15 minutes;
- the roles these need.

The stack tells the install what it made, with a one-time link that works for two hours, for one setup of your team. Nothing is copied by hand. S3 Vectors is the cheapest store Bedrock knowledge bases use: you pay for what is stored and searched, nothing while it sits idle.

Other ways stay on the page:
- **An existing one** lists the knowledge bases in the install's account. The same stack adds the data source and schedule to the one you pick.
- **A custom data source** pushes documents directly.
- **Enter it yourself** keeps the fields for a stack you deploy on your own.

The self-hosting guide has the details: [Bedrock knowledge bases](/self-host/bedrock).

A self-hosted install can also push into a custom data source of a knowledge base in another AWS account it has connected, the same way as CoderHelm cloud.

### Status

The section shows the last sync, how many documents are in Bedrock, what the last sync added, updated and removed, and any problem in plain words. **Sync now** runs one at once; otherwise CoderHelm syncs every 15 minutes and right after you save.

## Limits

- Bedrock takes 10 documents per direct ingestion call and 6 MB per request; CoderHelm sends at most 10 documents and 5 MB per call, and a document longer than about 4.5 MB is cut there (the status says which). [Quotas](https://docs.aws.amazon.com/general/latest/gr/bedrock.html)
- A metadata file beside an S3 document is at most 10 KB; CoderHelm shortens long titles and links to fit.
- A Bedrock data source runs one ingestion job at a time, and StartIngestionJob is limited to one call every 10 seconds per account.
- Web crawler data sources can't sign in to a site, so they can't read your private pages. Since September 30, 2026, new knowledge bases you manage yourself can only add S3 and custom data sources ([connectors](https://docs.aws.amazon.com/bedrock/latest/userguide/data-source-connectors.html)).
- A connection reads at most 300 calls a minute.

## Costs

CoderHelm doesn't charge for either way. AWS charges you in your own account:

- **AgentCore Gateway**: $0.005 per 1,000 calls to list or invoke tools, $0.025 per 1,000 searches, and $0.02 per 100 tools indexed a month. AgentCore Identity adds no charge when used through the gateway. ([AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/))
- **Bedrock knowledge base**: the knowledge base itself is free. You pay for the embedding model while documents are indexed (Titan Text Embeddings V2 is $0.02 per million tokens in us-east-1), for the vector store it uses (Amazon OpenSearch Serverless, S3 Vectors, Aurora and others, each priced by that service), and for any reranking or model calls when you retrieve. ([Bedrock pricing](https://aws.amazon.com/bedrock/pricing/))
- **S3 folder** (self-hosted): S3 storage and requests for the copies, which are small next to the vector store.
- **The one-button stack** (self-hosted), in us-east-1. A team with a few thousand documents usually pays well under $1 a month. ([S3 pricing](https://aws.amazon.com/s3/pricing/))
  - S3 Vectors: $0.06 per GB a month stored, $0.20 per GB written, and $2.50 per million searches.
  - Titan Text Embeddings V2: $0.02 per million tokens.
  - The schedule and the reporter: within AWS's free tiers.

Prices are AWS's as of November 2026; check the linked pages for your region.
