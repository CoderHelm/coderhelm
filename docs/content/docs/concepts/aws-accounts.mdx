title: AWS accounts

Connect an AWS account and CoderHelm reads its CloudWatch logs every 6 hours, groups the errors it finds and suggests fixes. The same connection lets agents read alarms, CloudWatch metrics, Airflow (MWAA) and the ECS services behind a log group while they work. Everything stays read-only: CoderHelm can list, describe and query, never change anything in your account.

## Connect an account

Open **Settings**, then **Integrations**, then **AWS** (admins only). You need permission to create an IAM role in the account.

<Steps>
<Step>

### Create the role

**Open the stack in AWS** opens CloudFormation with a stack that creates one role, `CoderHelmLogReader`, and nothing else. Review it and press **Create stack**. The role trusts CoderHelm's AWS account only with your team's **External ID**, which the stack fills in, so no one else using CoderHelm can take it on.

Prefer to make it yourself? Choose **I'll make it myself**: the page lists the account to trust, your External ID and every action the role needs, grouped by what CoderHelm reads with it. You can also download the template.

</Step>
<Step>

### Paste its ARN and region

Copy **RoleArn** from the stack's **Outputs** tab, paste it with the region of your logs, and press **Check and connect**. CoderHelm takes on the role once to check it before saving.

</Step>
</Steps>

## What the role can read

- **CloudWatch logs and alarms**\
  Error lines and alarm states, so CoderHelm can find what broke and propose a fix.
- **CloudWatch metrics**\
  Error rate, latency and other metrics before and after a deploy.
- **Airflow**\
  DAG runs, task logs and import errors, as Airflow's Viewer role, which can't trigger or change anything.
- **ECS services and tasks**\
  Which tasks behind a failing log group are running, since when and how they start, as evidence before a fix.
- **Finding the code behind a log group**\
  Function, image and stack tags, to work out which repository a log group's code lives in.
- **Checking its own permissions**\
  IAM's policy simulator, on this one role only, so the page can say when an update is needed.

CoderHelm keeps only the findings and their error patterns, never raw log lines.

## Log findings and automatic fix PRs

Every finding shows on the **Logs** page with how often and when its error happened. Press **Create fix PR** on any finding to start a fix run, or let CoderHelm open them by itself.

The card at the top of the Logs page says whether automatic fix PRs are on. While they are off, it says what turning them on does; **Turn on** switches them on for critical findings, up to 3 a day, and **Change what counts** opens the settings:

- **Open fix PRs automatically for**: critical findings (the default), warning and critical findings, or every finding.
- **Up to N a day**: the most fix runs started automatically in a day (UTC), from 1 to 20.
- **Which log groups**, each log group's repo and its own switch and severity, and **quiet hours** when no automatic run starts.

Once on, the card is one line, for example "On: critical findings get a fix PR automatically · 1 of 3 today · posted to Slack · Settings". Only findings first seen after it is turned on get one, there is never more than one open run or PR for the same error, and nothing merges without a person's approval. A finding that would get one says so in the list; one that got one shows **Auto** and its PR.

### Where fix PRs are posted

Fix PRs from findings, started automatically or by hand, post where new findings post. Until someone chooses otherwise, that is the team's alert channel, the same Teams or Slack channel production alerts post to (**Settings**, then **Alerts**, **Team channel and budget**). The automatic fix PR settings say where they post, or "Not posting anywhere" with a link to set up an alerts channel when none is set. Under **Post new findings to chat** you can instead pick channels of their own, or turn posting off; that choice stands.

Each fix PR posts one card: the finding's title and severity, its log group, how many lines and when it was first and last seen, the PR and its repository, one line on what it changes, and links to the PR and the finding. A finding's card posts once, even when its run is retried. When the PR merges or is closed, one follow-up card posts in the same channel and names the card it follows; Teams and Slack webhooks can't reply in a thread or edit a posted card.

## Keeping permissions up to date

When a CoderHelm release reads something new, the role needs the matching read-only permission. Each connected account shows its state:

- **Permissions up to date**\
  The role has every permission this release uses.
- **Update needed: N new read-only permissions**\
  The page lists what each new permission lets CoderHelm read, and why.

To update, sign in to the AWS account the role is in and press **Update in AWS**. It opens a small stack, `CoderHelmLogReaderUpdate-<id>`, that adds exactly the new permissions to your existing role. Review it and press **Create stack**. When you come back, the page checks again by itself and shows the result. If something went wrong, it says why in one sentence with the fix, for example:

- the stack was created in a different AWS account from the role's;
- the stack failed (the stack's **Events** tab has the cause);
- a permissions boundary on the role, or an organization policy (SCP), blocks the permissions.

With several accounts, the page lists every account's state with an update link for each. Admins hear once in the team's Slack or Teams channel when a release needs an update. Until then, steps that need a missing permission are skipped and say so, and everything else keeps working.

## Alerts from AWS

To start work from CloudWatch alarms, add an alert route under **Settings**, then **Alerts**, and subscribe your SNS topic to the address it shows. Save and turn on the route first: CoderHelm only confirms subscriptions for topics with a route that's on. See [Webhooks](/api/webhooks) for how messages are verified.

### Alarms that keep firing

An alarm that flips between OK and ALARM can post over and over. Each route has a setting, **When an alarm keeps firing**, and a CloudWatch alarm can have its own:

- **Every time it fires** (the default): each alarm posts. Routes saved before this setting work this way.
- **Once, until it clears**: the first alarm posts. While it keeps firing nothing more posts, and no second fix run starts.
- **Once, then a daily reminder**: the same, plus one message a day saying it is still firing, since when and how many times.

An alarm has cleared once it stays OK for 30 minutes, or two of its own evaluation spans when that is longer (up to 6 hours). Going back to ALARM inside that window still counts as the same firing. After a real clear the recovery posts once, if the route posts recoveries, and the next alarm posts right away. Every firing is still recorded; the Alerts page shows them as one row with a count.

## Running your own install

On a self-hosted install, the role trusts **your install's own AWS account**, never CoderHelm's, and the stack links come from your install's release. Reading the install's own account works the same way. See [Integrations](/self-host/integrations) in the self-hosting guide.
