The **app map** shows how your team's app fits together across every repository CoderHelm works in: its parts, what calls what, the screens and everything behind them, and the outside services it uses. It is written in plain words, so people who don't read code can follow it.

Open **App map** in the menu, beside Chat and Knowledge (or search for it with Cmd+K). The first visit starts the first build. While it builds, the page lists the steps (reading the repositories, finding the parts and how they connect, describing each part, done) with the one it is on, when it started, and how long a map of your number of repositories usually takes; it fills in by itself, and you can leave the page meanwhile. If a build stops, the page says at which step, with one **Try again**.

Map viewer and extractor from the open-source [Floorplan](https://github.com/haydenschmitty/floorplan) project, MIT. CoderHelm runs a pinned Floorplan release and adds its own Recent work and Health, and Chat answers questions from it.

## What is on it

Floorplan reads every repository side by side and finds:

- **parts**: the app's main pieces, chosen and named in plain words, each with its files;
- **endpoints** the servers answer and **web requests** the apps make, matched to each other by method and address, across repositories too;
- **screens**, with everything behind each one: the code it uses, the requests it sends, the server code that answers and the outside services behind it;
- **outside services** from the packages and hosts the code uses (Stripe, AWS, SendGrid, Supabase, Firebase, Sanity and others);
- a short tour, and a name and one-line description for every file and endpoint.

The map's own search, Screens, tour and Health buttons work as they do in Floorplan. A connection Floorplan worked out from a request's address rather than from an import is shown as inferred.

## Recent work and Health

Two switches under the map add what CoderHelm knows, in the map's own Recent work and Health panels:

- **Recent work** marks the files CoderHelm's runs of the last two weeks changed, each run with its ticket, why (from the run's plan) and its pull request.
- **Health** adds CoderHelm's open security findings, infrastructure findings, log findings and alerts on the files and parts they concern, each linking to its finding in CoderHelm. Floorplan's own checks stay too, marked **Floorplan check**; one that names the same file and line as a CoderHelm finding is shown once.

## Ask about the map

Questions about the map are answered by [Chat](/concepts/chat), and kept with your chats:

- Type a question in the box under the map ("what happens when someone books a slip?"). Chat answers from the map first, in numbered steps for how something happens, and reads the code for exact lines. The answer shows the parts it involves as a small map, and **Continue in Chat** opens the chat to keep going.
- Pick **Ask about this** on a card in the map to start a new chat about that part, with the question ready in the box.
- In Chat, any question about how your app fits together ("how does checkout work?", "what calls the bookings endpoint?", "what's behind the slip page?", "which service charges the card?") uses the map the same way. **Open in App map** under such an answer opens this page on the parts it involves.
- AI tools connected through [/mcp](/mcp) can read the map too (`map_overview`, `map_find`, `map_part`, `map_screen`, `map_file`, under `code:read`).

## How it is made and kept current

- CoderHelm runs Floorplan's scripts in its code sandbox on a snapshot of the team's repositories, and does Floorplan's writing jobs (choosing the parts, describing files and endpoints) with your team's own model. Their cost is recorded under **App map** in Analytics.
- After a push to a default branch, the map is brought up to date with Floorplan's own update: unchanged files keep their descriptions, and only new or changed files and endpoints are described again. Nothing is redone when no default branch moved.
- The map keeps names, paths and short descriptions, never your source files. The viewer runs in a sandboxed frame on the page with no network access of its own.
- Above the map the page says when it was built and from how many repositories. Admins can build it again with the small **Build the map again** button there.
- One build runs at a time per team. While one is queued or running, the button is hidden and the page says what the build is doing; pressing it twice, or a second admin pressing it at the same time, never starts a second build.
- The map's layout keeps lines clear of the cards they don't join and spaces the lines that meet one card apart. The title and description of what the map shows (the app, or the part you opened) sit above the map, never over its cards.
- **Full screen** (the button with outward arrows, under the zoom buttons) puts the map on the whole screen; press it again or Esc to come back. The button with four corners fits the map to its frame.
- The page reads the map straight from your install's storage once per build, and only Recent work and Health from the API, so a large map opens quickly. If a read takes longer than 20 seconds, the page says so with **Try again**.
