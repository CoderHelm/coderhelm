## Skills

A plugin's skills are ordinary [SKILL.md files](/concepts/skills#frontmatter): a name, a description that says when to use it, and instructions. They apply only to this plugin's runs; other plugins and the coding agents don't see them.

Use skills for what stays true across runs: the brand voice, a checklist, the format of a support reply.

## Agents

An agent file is Markdown with frontmatter. The body is the agent's instructions for a run.

<include meta='title="agents/launch-writer.md"'>../../../examples/marketing/agents/launch-writer.md</include>

| Field | Meaning |
| --- | --- |
| `name` | The agent's id. Defaults to the file name. A trigger's `agent:` names it. |
| `description` | One line saying what it does. |
| `tools` | The tools it uses. Each must be granted in `plugin.yaml`; the [validator](/plugins/testing) refuses any that aren't. |

The plugin's page in the dashboard lists its skills and agents under **Skills and agents**.

## Tools

Tools are declared in the manifest's `tools` list, in one of two shapes.

**Tools from an MCP server** on the team's [Connections](/concepts/connections) page. List the tool names, or narrow patterns such as `get_*`, the plugin may call; every other tool on that server is hidden from the run. `allow` is required and may never be `*`: a plugin never gets every tool of a server.

```yaml
tools:
  - ref: "mcp:sanity"
    allow: [get_*, list_*, query_*, create_draft]
```

**HTTP tools** the plugin defines to call an outside service over HTTPS with one of the team's [connections](/plugins/connections). The token comes from the connection; the manifest never carries credentials.

```yaml
tools:
  - name: publish_post
    kind: http
    connection: linkedin            # a `connection` setting
    method: POST
    url: "https://api.linkedin.com/rest/posts"
    risk: consequential
    description: Publish an approved post on LinkedIn.
    headers:
      LinkedIn-Version: "202406"
    body:
      author: "{{setting:linkedin_author}}"
      commentary: "{{content}}"
```

- `headers` are extra request headers, such as an API version. `Authorization`, `Cookie`, `Host`, `Content-Length`, `Transfer-Encoding` and `Proxy-*` are refused.
- `body` is the JSON to send. Strings may use `{{title}}`, `{{content}}`, `{{kind}}` and `{{channel}}` from the approved draft, and `{{setting:<key>}}` for a `string` setting that isn't sensitive. Values are inserted as text inside JSON strings, so a draft can never add keys or change the shape. Without `body`, CoderHelm sends `{title, content, kind, channel}`.

**Built-in tools** (`kind: builtin`): one of CoderHelm's own read-only tools, by name, such as `search_code`. A plugin can't add a built-in that writes.

Every run also has two tools without asking: `read_plugin_skill` (its own skills) and `save_draft` (drafts kept in CoderHelm until a person approves them).

The plugin's page shows every tool and its risk under **What it can do**.

## Risk levels

Every tool has one of three risk levels. CoderHelm works a tool's risk out from its name and method: a name starting with a read verb (`get`, `list`, `search`, `query`…) is `read`; one with a word like `publish`, `send`, `post` or `delete` is `consequential`; anything else, and any HTTP call that isn't a `GET`, is at least `write`. A `risk:` in the manifest can raise a tool's risk, never lower it.

| Risk | Means | Runs |
| --- | --- | --- |
| `read` | Only looks: search, fetch, list. | Whenever the agent calls it. |
| `write` | Changes something a person can still review before anyone sees it, such as a draft in a CMS. | Only if the team lets plugins save drafts without a person (below). |
| `consequential` | Reaches people or money: publish, send, post. | Only through a `publish` output, after a person approves the exact version of a draft. |

## What may happen without a person

Each team chooses, on the **Plugins** page, the most a plugin may do on its own:

- **Plugins only read without a person**: every write waits for a yes too.
- **Plugins may save drafts without a person** (read and save drafts).

Publishing, sending and posting always wait for an approval, whatever the team picks.

A tool missing from the manifest can't be called, by any agent, in any run.
