The [install guide](/self-host/install/) opens AWS on a CloudFormation stack. This page lists everything that stack creates in your account, what each part is allowed to do, and what that means for you. Read it before you press **Create stack**.

In short: CoderHelm is one CloudFormation stack in your account. You update it with a stack update and remove it by deleting the stack. Every role it creates carries a permissions boundary that keeps it to CoderHelm's own resources. Updates are applied through one deploy role that only CloudFormation can use, limited to this install's resources. CoderHelm the company gets no access to your account.

## What gets created

### One stack

A CloudFormation stack named `coderhelm-<name>` (the name in your AWS account, `prod` unless you change it). The parts of CoderHelm are nested stacks inside it (database, storage, API, worker, streaming, web, email, updates, monitoring, log analyzer). CloudFormation creates, tracks and deletes all of them. The stack runs with your own AWS permissions, or with a CloudFormation service role you choose in the console. Its **Outputs** show your address when it is done.

### The permissions boundary

A managed policy, `coderhelm-<name>-boundary-stack`. It is the most any CoderHelm role can do, whatever its own policy says. Every role the stack creates carries it; the deploy role carries an identical copy, `coderhelm-<name>-deploy-boundary-stack`, which is kept with that role when you delete the stack. Even within the AWS services CoderHelm uses, it refuses:

- creating IAM users, access keys, sign in profiles, groups or identity providers;
- anything in Organizations, account settings, CloudTrail or GuardDuty;
- any IAM action on a role or policy whose name doesn't start with `coderhelm-<name>-`;
- creating or changing a role without this boundary on it, and removing the boundary from any role;
- changing or deleting the boundary itself, or changing the deploy role;
- assuming any other role in this account, except CoderHelm's two read roles (`CoderHelmLogReader` and `CoderhelmReadOnly`), and those only by the gateway's and worker's roles.

### The release bucket

A private S3 bucket, `coderhelm-<name>-release-<account>`, with the release's part templates and code. The template you launch lists the SHA-256 of every one of those files. Before any part is created, the install helper downloads each file from CoderHelm's public release location, checks it against that list, and writes only the files that match. The parts and their functions then read only from this bucket. Since the template itself is covered by the release's signed checksums, checking the template checks everything.

### The install helper

A Lambda function, `coderhelm-<name>-install-helper`, whose code is inside the template. It backs the stack's custom resources: copying the release files, storing the one time setup key in the install's secret, adding the first admin to the sign up list, asking the updater for your domain's certificate, writing the progress file, and on delete releasing a hybrid install's CoderHelm address, emptying buckets, deleting tables and removing log groups. Its role carries the boundary and reaches only this install's names: the release bucket, buckets named `coderhelm-<name>-*`, the install's secret and tables, the updater function, its own stack, its own log group, and log groups named for the install. It cannot create log groups, so nothing it does after a delete leaves one behind.

### The secret

A Secrets Manager secret, `coderhelm/<name>/secrets`. CloudFormation makes it with a random session signing key and empty GitHub App fields. Its template never changes, so updates never regenerate it.

### The deploy role

The stack adds `coderhelm-<name>-deploy-stack`, a role only CloudFormation can use, limited to resources named or tagged for this install, with its own copy of the boundary on it. The role and its copy are kept when you delete the stack (CloudFormation keeps using a stack's role, and a role can't delete itself); `leftovers` lists them and `--delete` removes them. The updater may hand it only to CloudFormation, and only for a change set on this stack from a published CoderHelm release template. It applies an update when an install admin presses **Update** in Settings, then System, or in the maintenance window when automatic updates are on (they are off by default). A change that would replace or remove data or change permissions waits for an admin to confirm it there, and a change to this role or a boundary is never applied by CoderHelm: someone with administrator rights executes it in the CloudFormation console. On releases up to v0.8.26, the role existed only with automatic updates on.

### Progress, and nothing public

The stack reports its phase, a plain message and, at the end, its address to CoderHelm, with a key the install guide made in your browser. Only a browser with that key can read it back, and CoderHelm keeps it for 14 days. No emails, keys or account numbers are in it. Nothing in your account is public: releases before this one kept the progress in a public bucket, `coderhelm-setup-<id>`, which the install helper deletes on the stack's first update.

### CoderHelm itself

- Lambda functions and an HTTP API: CoderHelm itself, paid per use. Each function's log group is part of the stack.
- DynamoDB tables, an S3 data bucket, SQS queues and KMS keys: your runs, settings and files, encrypted.
- CloudFront and a Cognito user pool: the web address and sign in.
- CodeBuild projects: a build sandbox for your repositories' own build scripts, and a read only release check that verifies a new release's signature. Neither can deploy anything.
- An updater function that looks for new releases every hour, prepares and applies each update as a change set, and emails your admins only when one needs them or something went wrong (plus an optional weekly digest of what's new).
- An IAM role for each service, with only the tables, queues, keys and actions that service uses. [Security model](/self-host/security/) lists them.

Every one of those roles carries the boundary.

### What it costs

The install guide shows the monthly AWS estimate for your choices before you launch. Most of it scales with use. Model calls are extra: on this AWS bill with Bedrock, or on each team's Anthropic bill with API keys.

## What CoderHelm the company can do

Nothing in your account. The stack creates no role for another account, and nothing it creates trusts an account outside yours. There is no support login and no license check.

What reaches CoderHelm depends only on what you turn on:

- **Hybrid** (a CoderHelm address, CoderHelm's GitHub App, CoderHelm's Jira app, or email through CoderHelm) adds no AWS access. CoderHelm passes GitHub and Jira events to your install and points your address at your CloudFront. [What CoderHelm sees](/self-host/hybrid/#trust-model) lists each part and what CoderHelm keeps.
- **Other AWS accounts a team connects later** trust your install's own account, never CoderHelm's. See [Integrations](/self-host/integrations/).

## The setup key and the two links

The install guide makes three random values and puts them in the link that opens AWS:

- **The progress ID and key** let the stack report its progress to CoderHelm and the guide read it back. The key is a hidden stack parameter (NoEcho) and stays in your browser. The guide's own link (`/self-host/install/?id=...`) holds only the ID, the region and the install name: without the key it shows nothing.
- **The setup key** is one time. It lets the guide hand your new GitHub App's keys straight to your install. It stops working once the app exists. The stack parameter hides it (NoEcho).

The AWS link holds the setup key and your email. Don't share that link or paste it anywhere.

## Risks and how to reduce them

### CoderHelm can act within its boundary

Whoever can change CoderHelm's functions or its IAM roles can do what the boundary allows. Changing those already takes administrator rights in your account.

- Keep Lambda and IAM rights to the people who already administer the account.
- Install in an AWS account of its own, if you can.

### A malicious release could change CoderHelm

Every update is a stack update to a release's template, shown first as a change set: what each part adds, changes, replaces or removes. Settings, then System shows its summary and a link to it in the console. Before the updater prepares one, a read only build checks the release's signature, and the updater checks the template it downloads against that signed checksum. You can [check a release yourself](/self-host/updates-security/) before you launch or apply it.

If CoderHelm's release pipeline were ever broken into, a malicious release you applied could change any CoderHelm resource, within the boundary. It could not create an admin role or an IAM user, touch IAM outside `coderhelm-<name>-*`, or switch off CloudTrail or GuardDuty.

- Automatic updates are off unless you turn them on in the install guide's **More options**. With them off, a release is applied only when an install admin presses **Update**, and anything that changes data or permissions waits for an admin to confirm it.

### Deleting the stack keeps your data unless you say otherwise

The stack parameter `KeepDataOnDelete` is `true` by default: deleting the stack keeps the tables, the data bucket, the KMS keys, the user pool and the secret. A first launch that fails and rolls back still removes everything it made. To delete the data too, set `KeepDataOnDelete` to `false` with **Update stack** first. See [Uninstall](/self-host/uninstall/).

### Progress goes through CoderHelm

The stack sends its progress to CoderHelm (api.coderhelm.com). If your install can't reach it, the install still runs, and the guide asks for your address from the stack's **Outputs** tab.

### A leaked AWS link exposes the setup key

Until your GitHub App exists, someone with the setup key could give your install a GitHub App of their own. Share the guide's own link instead, and finish the GitHub step soon after the install answers.

## Remove everything

1. **Delete the stack** `coderhelm-<name>` in CloudFormation. With `KeepDataOnDelete` left at `true`, your data stays. Set it to `false` first to remove that too (KMS keys after AWS's 7 day wait). The [uninstall page](/self-host/uninstall/) walks you through it.
2. **Check nothing is left:** `npx -y github:CoderHelm/coderhelm-platform leftovers --stage <name> --region <region>` lists, read only, anything still named or tagged for the install. Once an update ran, the deploy role is listed: a role can't delete itself, so it stays.
3. **Uninstall and delete your GitHub App** on GitHub.

## Installed before one-stack releases

An install made by an earlier Launch Stack is several stacks (`coderhelm-<name>-database`, `-api` and so on) plus that Launch Stack's boundary, deploy role and assets bucket. Move it to one stack, data kept, with `coderhelm-selfhost migrate`. See [Migrate to one stack](/self-host/migrate/).
